# Architecture

## Scope

GymPro v2 is a server-rendered PHP application with a MySQL persistence layer. Its principal design constraint is an exact ten-table application schema. That boundary keeps deployment, review, and teaching use straightforward while preserving database constraints around the important business relationships.

## Layers

- **HTTP and CLI entry points** validate input and select a use case.
- **Application services** enforce permissions and business transitions such as activating a membership or enrolling a member.
- **Bootstrap helpers** provide configuration, `db()`, `db_one()`, `db_execute()`, and `transaction()`.
- **MySQL** owns durable identity, foreign-key integrity, uniqueness, and transactional updates.

Entry points should not concatenate user input into SQL. Prepared helper calls carry values separately from statements. Multi-record state changes run inside `transaction()`.

## Domain boundaries

The ten tables form five connected areas:

- Identity: `USER_ACCOUNT`, with optional one-to-one links to `MEMBER` or `TRAINER`.
- Membership: `MEMBERSHIP_PLAN`, `MEMBERSHIP`, and `MEMBERSHIP_PAYMENT`.
- Scheduling: `GYM_CLASS`, assigned to a `TRAINER`.
- Participation: `CLASS_ENROLLMENT`, `CLASS_ATTENDANCE`, and `GYM_VISIT`.

Operational traceability is handled by application logs rather than an eleventh database table.

Role values are `ADMIN`, `RECEPTIONIST`, `TRAINER`, and `MEMBER`. Authorization is application-enforced; foreign keys ensure referenced profiles and actors exist.

## Data integrity strategy

- Natural identifiers such as account email and payment reference are unique.
- A member may enroll in a class only once.
- Class attendance is attached to an enrollment and repeats the class identifier for simple reporting; application logic must keep it consistent with the enrollment.
- Historical payments and memberships use restrictive deletes. User-facing removal should normally be a status transition rather than physical deletion.
- Attendance corrections retain a reason and the actor instead of deleting history.

## Runtime and security

Secrets belong in local environment configuration and must not be committed. Passwords are stored only as hashes generated by `password_hash()`. Mutating web requests require CSRF protection, output is escaped by default, and sessions use HTTP-only, SameSite cookies. Production deployments should enable HTTPS and secure cookies.

The demo seeder is deliberately CLI-only and local-only. It contains no real identities, uses `example.test`, and performs only idempotent inserts/updates inside one transaction.
